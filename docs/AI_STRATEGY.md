# Quoridor AI 策略与实现

本文记录本项目双人 Quoridor AI 的设计。搜索核心位于 `src/ai.js`，异步 Agent 和 Worker
边界位于 `src/agents/` 与 `src/workers/`，规则、合法动作和寻路由 `src/game.js` 统一负责。
AI 不复制一套规则，避免搜索中的模拟局面与真实游戏产生差异。

## 1. 问题性质与总体方案

双人 Quoridor 是确定性、完全信息、轮流行动、零和游戏。单独使用 BFS 或 A* 只能回答
“当前最短路是什么”，无法处理对手下一回合会主动阻挡的问题。因此本项目组合使用：

1. BFS 最短路作为局面特征；
2. Negamax 博弈搜索；
3. Alpha-Beta 剪枝；
4. 迭代加深与时间预算；
5. 置换表缓存重复局面；
6. 墙候选筛选和强动作排序，控制最大的分支来源。

`chooseAIMove(state, options)` 是同步函数，返回：

```js
{
  action,     // 合法动作，终局或没有动作时为 null
  score,      // 从当前 AI 视角得到的分数
  depth,      // 最后完整搜索结束的深度
  nodes,      // 本次调用访问的节点数量
  elapsedMs,  // 实际耗时
}
```

支持的选项包括：

```js
{
  difficulty: 'easy' | 'medium' | 'hard',
  timeLimitMs: 350,
  random: Math.random,
  maxDepth: 3,
}
```

`random` 只用于简单难度的有限随机失误，可以传入固定 RNG 复现实验。`maxDepth` 主要用于
测试和性能分析，正常 UI 只需设置难度和可选的时间限制。

`chooseAIMove` 是底层同步搜索函数，只在经典 AI adapter 或 Worker 内调用。产品 UI 使用统一
的异步接口：

```js
Agent.choose(state, options, signal) -> Promise<{
  action,
  value,
  simulations,
  nodes,
  elapsedMs,
  engine,
  depth,
  score,
}>
```

`ClassicWorkerAgent` 在模块化 Web Worker 中运行 Negamax。Abort、请求抢占或 5 秒硬超时时会
终止正在同步搜索的 Worker，并在下一次请求时重新创建，因此主线程无需等待旧搜索返回。

## 2. 状态与动作

规则引擎使用以下核心状态：

```text
pawns[2]              两枚棋子的位置
wallsRemaining[2]     双方剩余墙数
horizontalWalls       横墙集合
verticalWalls         竖墙集合
currentPlayer         当前行动方
winner                胜者或 null
moveNumber            已行动回合数
```

AI 搜索的动作与 UI 完全相同：

```js
{ type: 'move', row, col }
{ type: 'wall', orientation: 'h' | 'v', row, col }
```

`applyAction` 会克隆并返回新状态，搜索不会改写 UI 持有的真实局面。`serializeState` 提供稳定
的状态键，用于置换表。

## 3. 合法动作生成

AI 只从 `getLegalActions` 返回的动作中选择。规则引擎负责：

- 普通上下左右移动；
- 相邻棋子后的直跳；
- 直跳方向被墙或边界挡住时的斜跳；
- 墙不越界、不重叠且不交叉；
- 玩家仍有墙可放；
- 放墙后双方至少各有一条到目标边的路径。

最后一项通过 BFS 可达性检查完成。做封路检查时，棋子不被视为永久障碍；棋子会在以后回合
移动，墙才是改变棋盘连通性的结构。所有墙动作在进入 AI 前已经通过该检查，因此候选剪枝
只影响强弱选择，不影响规则正确性。

## 4. BFS 距离

`shortestPathDistance(state, player)` 在 9x9 格点图上做 BFS：

- 每个格子是一个节点；
- 未被墙阻断的上下左右连接是边；
- 到达对面任意边格即到达目标；
- 返回最少步数，没有路线时返回 `Infinity`。

棋盘只有 81 个格子，BFS 的常数小，且无权图不需要 A*。AI 会分别计算己方与对手的最短
距离。合法放墙已经保证距离有限；实现仍对异常的无限距离做了防御性归一化。

## 5. 静态评估函数

非终局叶节点从指定玩家视角计算：

```text
score = 120 * (opponentDistance - ownDistance)
      +   7 * (ownWalls - opponentWalls)
      +   3 * (ownMobility - opponentMobility)
```

各项含义：

- **路径差**：己方越接近目标越好，对手绕路越远越好，是最主要因素；
- **墙数差**：墙是后续改变路径的资源，在距离相近时保留墙有价值；
- **机动性差**：合法棋子移动方向更多，通常较不容易被迫绕行。

终局不使用普通公式：

```text
胜利： +(1,000,000 - ply)
失败： -(1,000,000 - ply)
```

其中 `ply` 是当前搜索树中的半回合数。这让 AI 在都能获胜时选择更快的路线，在无法避免
失败时尽量延后失败。终局常数远大于任何合理的静态分数，不会发生“为了多留一堵墙而放弃
立即获胜”的情况。

该公式是实用启发式而非理论证明。权重应结合自我对弈数据继续校准，但当前权重已明确让
路径差主导墙资源和局部机动性。

## 6. Negamax 与 Alpha-Beta

双人零和搜索可以把 Minimax 写成更紧凑的 Negamax：

```text
score(action) = -negamax(nextState, depth - 1, -beta, -alpha)
```

每一层都站在当前行动方视角评分，因此进入对手回合时取负号。搜索过程维护 `alpha` 和
`beta`：当某动作已经证明当前分支不可能优于上层已知选择时，立即停止展开剩余兄弟动作。

根节点和内部节点还会直接识别“当前动作立即获胜”。这既减少一次递归，也确保极短时间预算
下不会错过终点前的一步。所有合法棋子动作都会保留，所以立即获胜不会被候选墙策略隐藏。

## 7. 迭代加深与时间控制

普通和困难难度依次完整搜索深度 1、2、3……，只有一层全部结束后才更新最终结果：

```text
depth 1 完成 -> 保存结果
depth 2 完成 -> 替换结果
depth 3 超时 -> 丢弃不完整结果，返回 depth 2
```

搜索开始前就保存了一个合法动作作为兜底，因此即使 `timeLimitMs` 为 0 或动作排序阶段超时，
也始终能返回合法动作。超时通过内部异常快速退出深层递归，不会把部分搜索误报成完整深度。

默认预算和深度上限为：

| 难度 | 最大深度 | 默认时间 | 根节点墙候选 | 深层墙候选 |
| --- | ---: | ---: | ---: | ---: |
| 简单 | 1 | 80 ms | 6 | 4 |
| 普通 | 3 | 350 ms | 9 | 6 |
| 困难 | 5 | 850 ms | 13 | 9 |

时间是硬性的墙钟预算目标，但 JavaScript 无法在一个正在执行的函数中被抢占；实现会在动作
排序、墙评估和固定数量的节点间隔处检查截止时间。一次极短的规则函数调用可能使统计耗时略
超过预算。UI 应在调用同步 AI 前先让浏览器绘制“思考中”状态。

## 8. 墙分支控制

一个棋子局面通常只有 2 到 5 个移动动作，但空棋盘可能有上百个合法墙动作。若每层全部
展开，深度很快失去意义。因此实现遵循“棋子动作全保留、墙动作择优保留”的原则。

### 8.1 几何预筛

先按墙到对手棋子的距离和轻微的中心性加分排序。普通和困难分别最多对 64、96 个墙候选
执行后续 BFS 评分。这个阶段只用于减少计算量，不直接决定最终落墙。

### 8.2 路径变化评分

对预筛后的每堵墙实际应用到克隆局面，再计算双方 BFS 距离变化：

```text
wallScore = 240 * opponentDistanceIncrease
          - 210 * ownDistanceIncrease
          + emergencyBonus
          + geometryScore
```

若对手距终点不超过两步，且该墙确实增加其最短路，额外加入紧急阻挡奖励。这样会优先考虑：

- 真正增加对手最短路的墙；
- 对自己的路线伤害较小的墙；
- 对手即将获胜时能马上改变距离的墙；
- 距离效果相同时，更接近当前冲突区域的墙。

最终只取表格所示数量进入搜索。墙本身消耗的资源对每个候选相同，所以墙数成本放在叶节点
评估，而不参与同一局面中不同墙之间的排序。

这种选择是选择性搜索：它显著降低浏览器响应时间，但理论上可能漏掉当前不改变最短距离、
数回合后才显出价值的战略墙。困难难度用更大的预筛与候选集合降低该风险。

## 9. 动作排序

Alpha-Beta 的结果不受动作顺序影响，但性能高度依赖先搜索强动作。当前顺序综合：

- 立即获胜的棋子移动；
- 让己方最短路缩短的移动；
- 增加对手距离、较少伤害自己的墙；
- 置换表中同一状态上次记录的最佳动作；
- 分数相同时使用稳定的动作序列化顺序，保证普通和困难模式可复现。

好的候选先搜索会更早提高 `alpha`，从而剪掉更多明显较差的回复。

## 10. 置换表

同一局面可能由不同动作顺序到达。每次 `chooseAIMove` 建立一张调用内置换表，键来自
`serializeState`，记录：

```text
depth       已完成搜索深度
score       局面分数
flag        EXACT / LOWER / UPPER
bestAction  当时的最佳动作
```

只有缓存深度不小于当前请求深度时才复用分数。精确值可直接返回；上下界值用于收紧
Alpha-Beta 窗口。即使缓存深度不足，`bestAction` 仍可用于动作排序。置换表限定在单次调用，
避免浏览器长时间运行后无界占用内存，也不需要处理跨局面老化。

## 11. 难度行为

### 简单

只做一层评估，并在分数最高的三个动作中按约 64% / 24% / 12% 加权选择。它仍会无条件
抓住立即获胜动作，但会产生可解释的次优选择。传入固定 `random` 可以让测试和演示可复现。

### 普通

默认搜索三层，墙分支控制较紧，适合本地浏览器中的快速对局。没有主动随机性；相同状态和
相同预算下，完整搜索得到的动作稳定。

### 困难

最多搜索五层，时间预算、预筛范围和墙候选数更大。迭代加深意味着复杂中盘不一定完成五层，
返回值中的 `depth` 会如实报告最后完成的深度。

## 12. 正确性与测试重点

AI 测试应覆盖：

- 返回动作属于规则引擎的合法动作集合；
- 站在目标前时选择立即获胜；
- 固定局面、固定深度下搜索结果可复现；
- 对手即将到达终点时会选择有效阻挡或更快获胜；
- `depth`、`nodes`、`elapsedMs` 等统计字段存在且合理；
- 极短时间预算仍返回合法动作。

规则层还应独立测试跳跃、斜跳、墙交叉/重叠、封死路径等，因为 AI 的合法性依赖规则引擎。

## 13. Worker 调度与生命周期

浏览器调度流程为：

1. UI 在下一动画帧提交当前状态，先让“思考中”状态完成绘制；
2. Worker 通过 structured clone 接收含 `Set` 和 `Map` 的棋局快照；
3. Worker 内的 `ClassicAgent` 调用同步 Negamax；
4. 主线程仅接受当前 request id 和当前 session 的结果；
5. 撤销、重开、新对局或页面关闭会通过 `AbortController` 取消请求；
6. 因同步搜索无法在 Worker 内处理中途消息，取消操作直接终止 Worker。

AI 对 AI 模式不再加入固定 3 秒等待。每一步仍从下一动画帧启动，以保证界面有机会渲染，
但不会人为延迟连续对弈。

## 14. 局限与后续方向

当前实现面向本地双人游戏，主要局限是：

- 静态评估只使用一条最短距离，没有直接衡量可替代最短路径数量；
- 选择性墙搜索可能漏掉延迟收益墙；
- 中止同步 Negamax 需要终止并重建 Worker，无法保留该 Worker 内的临时搜索数据；
- 置换表不跨回合保留，也未使用 Zobrist 增量哈希；
- 尚未加入 killer move、history heuristic、静态搜索或残局库；
- 权重来自工程经验，并非大规模自我对弈拟合。

可按收益与复杂度逐步改进：

1. 缓存 BFS 结果或使用增量墙图；
2. 加入多条最短路、关键割边和“必经通道”特征；
3. 跨回合保留有容量上限的置换表，或改用 Zobrist Hash；
4. 用自我对弈采样调整评估权重与墙候选数量；
5. 针对四人模式改用 Max-N、Paranoid Search 或 MCTS。

MCTS 对超大墙分支有吸引力，但纯随机 rollout 在 Quoridor 中质量通常不高，需要合理策略
引导。AlphaZero 类方法可用策略/价值网络配合自我对弈，不过训练、数据与部署成本显著高于
当前需求。对于零依赖、本地、响应快速的双人版本，BFS + 选择性 Negamax 是更务实的基线；
只有目标提升到高水平竞技 AI 时，才值得引入神经网络和强化学习训练管线。
